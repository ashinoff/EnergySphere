# ЭнергоСфера — контекст для ИИ-агентов

Единая рабочая платформа Сочинских электрических сетей: четыре независимых
модуля в одном приложении, одной базе и одном хостинге (экономия на отдельных
приложениях и базах). Интерфейс на русском.

| # | Модуль | Цвет | Источник логики |
|---|---|---|---|
| 01 | Анализ потребления (`analysis`) | зелёный | Analizator_PU_TP_v5_7 (портативный HTML) — во фрейме, без базы; карты тепла нет |
| 02 | Поиск потребителя (`consumers`) | синий | реестр как в Web_abonent_sochi (свой у каждого РЭС, грузит инженер РИРУ); монтёр ищет по № ПУ/ЛС, ставит геометку, фото объекта и ПСУ; инженер скачивает (ПСУ — PDF) и завершает, завершённые удаляются через 3 дня |
| 03 | Инструкция начальника РИРУ (`riru`) | охра | github ashinoff/strategy-to-action — сделан нативно: 3 плана с отметками, техкарты, нормативка/законы (PDF) |
| 04 | Акты ТП (`tp`) | лиловый | github ashinoff/TP_Approval — перенесён целиком (import-tp.mjs), интерфейс во фрейме /tp/ с темой Сферы |

## Стек и структура

Node 22 + TypeScript, Express 5, React 19 + Vite, PostgreSQL (pg), jose, zod — как
в TP_Approval, чтобы его код переезжал без переписывания.

```
apps/api/src/
  server.ts            старт: retry подключения к БД → миграции → seed прав → listen
  app.ts               маршруты ядра (вход, /me, админка), подключение модулей, раздача UI
  core/access.ts       КАТАЛОГ ролей и прав — единственный источник (web импортирует его же)
  core/access-service.ts  кто вошёл: учётка, роль, РЭС, права (кеш 30 с)
  core/keycloak.ts     проверка JWT (JWKS) и вход логин/пароль через сервер
  modules/index.ts     реестр модулей (/api/<module>/...)
apps/web/src/
  shell/               оболочка: дашборд → полосы + меню модуля (Shell.tsx), сфера-логотип
  modules/registry.tsx метаданные модулей: номер, цвета, иллюстрация, пункты меню и права
  admin/AdminPage.tsx  пользователи, матрица «роль × право», список РЭС
  ui/kit.tsx           ЕДИНЫЙ набор элементов (кнопки, поля, карточки…) — модули строятся только из него
  styles/              tokens.css (токены), ui.css, shell.css, login.css, admin.css
db/migrations/<core|module>/NNN_*.sql   core первым, затем модули; применённый файл не менять
```

## Инварианты (не нарушать)

- **Модули независимы.** Модуль не импортирует другой модуль; общее — только core
  (пользователь, РЭС, права). У каждого модуля своя схема БД (`analysis.*`,
  `consumers.*`, `riru.*`, `tp.*`) и свои миграции в `db/migrations/<id>/`.
- **Роль = область видимости, право = действие.** Роли с `scope:'res'` видят только
  свой РЭС (`user.resScope`), `scope:'all'` — все. Права роли — матрица в админке
  (`core.role_permissions`), плюс личные доп. права (`users.extra_permissions`).
  Администратор (`admin`) всегда имеет все права. Суперадмины — env `SUPER_ADMINS`.
- **Новое право:** ключ в `core/access.ts` → `requirePermission('ключ')` на роут →
  `can('ключ')` в интерфейсе (и `perm` у пункта меню в registry).
- **Вход только через платформенный Keycloak**, но его страница не показывается:
  форма → `POST /api/auth/login` → сервер сам ходит в Keycloak (Direct Access Grant
  клиента `web-desktop`). Учётка в нашей базе создаётся при первом входе со статусом
  «ожидает роли»; роль и РЭС назначает админ. Токены не логировать.
- **Внутри платформы (iframe)** — контракт `app-ready` / `platform-auth` с проверкой
  `event.origin`. `VITE_PLATFORM_ORIGIN` вшивается при сборке.
- **UI — по [docs/STYLE.md](docs/STYLE.md)** (обязательно перед любым экраном): без модальных окон; все кнопки/поля одного размера (`--control-h`);
  цвет модуля — только через `--tint/--accent/--accent-strong`. Десктоп в приоритете,
  телефон (монтёры) не ломать: `max-width: 900px`.

## Переменные окружения

`DATABASE_URL`, `PORT` (3000), `KEYCLOAK_URL`, `KEYCLOAK_REALM` (platform),
`KEYCLOAK_CLIENT` (web-desktop), `ACCESS_ROLE` (пусто — не требовать realm-роль),
`SUPER_ADMINS` (логины/e-mail через запятую), `PLATFORM_ORIGIN`,
`STORAGE_PATH` (/data/storage — файлы модулей), `AUTH_DISABLED` (только разработка),
`TP_RUNTIME_PASSWORD` (пароль служебной роли tp_runtime «Актов ТП», обязателен),
разовые: `TP_SETUP_DATABASE_URL`, `RESET_MODULE`, `RESET_DATABASE_URL`+`RESET_CONFIRM`.

## Создание актов ТП (modules/tp/acts — пишется вручную, импорт TP не трогает)

Акты и уведомления формируются из шаблонов отдела (Word со слиянием MERGEFIELD) без
Word. `assets/act-templates/<id>.docx` — 21 шаблон (бумага / ЭЦП / смена собственника),
готовятся `node --import tsx scripts/prepare-act-templates.ts` из папки «Создание
актов/шаблоны» (в git не входит — там реальные ТУ и акты): значения полей образца
стираются в «‹поле›», вписанные текстом данные заявителя (PATCHES) превращаются в поля.
- `catalog.ts` — шаблоны по осям вид × точка (опора / нижний ПУ / от опоры в ВРУ / РУ /
  ВУ) × учёт (прямой / ТТ) × мощность (≤15 / >15) × заявка (новая / увеличение); `pickTemplates`.
- `fields.ts` — словарь полей с источником (ТУ / инженер / ПУ-ТТ / расчёт) и `actValues()`.
- `merge.ts` — `fillTemplate()` заполняет поля (и в надписях схемы), отвязывает их и снимает
  mailMerge; поле без значения очищается (данные образца в акт не попадают).
- `compute.ts` — прописью, сумма с НДС (формат списков отдела), дата, склонение ФИО.
- `losses.ts` — потери в линии как лист «Потери» (РУ/ВУ, кабель).
- `signer.ts` — подписант: фраза «в лице … действующей на основании доверенности №… от …» и подпись
  «/И.О. Фамилия/» из справочника доверенностей TP (в шаблонах — поля «Подписант» и
  «Подписант_подпись» вместо вшитого человека; строки согласования без «/…/» — текст шаблона).
- Подготовка шаблонов убирает ещё: картинки штампа ЭЦП прошлого подписания в уведомлениях
  («ПОДПИСАНО ЭЛЕКТРОННОЙ ЦИФРОВОЙ ПОДПИСЬЮ… Владелец: …»), ссылки слияния на файлы сотрудников,
  авторов файла. Проверка — тест «нет штампов ЭЦП и ссылок на файлы».
- `losses-doc.ts` — лист «Расчёт потерь» в конце документа вместо метки ‹РАСЧЁТ_ПОТЕРЬ›.
- `tu-facts.ts` — из ТУ: объект, мощность, ТП, фидер, ПС, заявка, пункты 10.x/11.x (по нумерации Word).
- `render.ts` — сборка; `routes.ts` — API `/tp/api/v1/act-builder` (монтируется в mount.ts до TP):
  карточки, каталог, анкета из карточки и ТУ, ПУ из «Учёт ПУ», предпросмотр, Word.
- Страница Сферы `apps/web/src/modules/tp/ActBuilder.tsx` (пункт «Создание акта по ТУ»): карточка →
  схема (вид / точка / учёт) → анкета «Из ТУ / Заполняет инженер / ПУ и ТТ / Посчитано» →
  «Скачать Word» или «Сформировать и отправить в маршрут» (обычные запросы TP: файл → версия).
  Уведомление ЭЦП только скачивается: маршрут принимает его в PDF.
- Word упаковывается без записей-папок (`packDocx`): проверка загрузки TP отклоняет путь «word/embeddings/».
- «Учёт ПУ»: `GET /api/service/pu?contract=` с `X-Service-Key` (ветка es-act-service);
  в Сфере `SVETLYACHOK_URL`, `SVETLYACHOK_KEY`.
Проверки: `tests/acts.test.ts` (акт Обуховича из своей строки Excel = оригинал по тексту; все 21
шаблона проходят validateDocx), `tests/tp-acts.test.ts` (сквозной: ТУ → анкета → Word → версия 1).
Под администратором Windows встроенный Postgres не стартует — `TEST_PG_PORT=<порт>` берёт
уже запущенный (pg_ctl сам понижает права; пароль postgres).
